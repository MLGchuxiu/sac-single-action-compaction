# 第二轮：按预期收益优化，并在百万级上下文任务上验证

> 承接 [`REPORT.md`](REPORT.md)（第一轮：论文复现 + v1–v4 迭代）。
> 本轮回答两个问题：**我提出的优化方向哪些真的有效？百万级上下文的编程任务需要长上下文吗？**
> 约束不变：输入 ≤ **130,172** tokens，输出 ≤ **8,192** tokens；模型 qwen3.7-flash / deepseek-v4.1-flash。
>
> 说明：本轮还包含一组基于真实工作会话的结构回放与状态保真度实验，结论已并入正文
> （真实长会话下 FHA/EoCC 均无法守住 130K 预算，只有 SAC 全程不超限；机器命令账本把状态保真度
> 从 0.19 提升到 0.90）。会话原始数据与明细表未包含在本仓库。

## 0. 结论摘要（TL;DR）

1. **最大的收益来自"把状态更新并进动作调用"（v6）**，不是更聪明的摘要：请求数 **485→156**（qwen，−68%）、
   输入 token **1.03M→0.39M**（−62%），并且 qwen 从 5/8 提升到 **8/8**。两个模型在 8 个任务上首次全绿。
2. **百万级上下文的编程任务根本不需要长上下文**：一个 **992,136 token / 1,287 文件 / 3.57 MB** 的仓库，
   全历史基线只用 **8–10 次请求、峰值 3–4.2K** 就修好了；SAC 反而多花 **2–8 倍**请求。
   这正是论文 RQ2 的结论——长输入不等于长上下文，选择性阅读才是主力。
3. **状态保真度是 SAC 的真实短板，而机器账本是解药**：在真实会话的保真度测试中，让模型只凭压缩后的状态
   回忆执行过的命令，论文模板 v1 平均只有 **0.19**；把命令交给 harness 维护（v8/v9 全量账本）后升到
   **0.73 / 0.90（约 4–4.7 倍）**。压缩确实会丢细节（论文 §3.1），但"哪些事实该由机器记"是可以工程化解决的。
4. **四轮迭代的结论可以合成一个版本**：v6（内联状态）解决"怎么写状态更省"（请求 −68%）；
   全量命令账本解决"哪些事实不该由模型写"（保真度 0.19→0.90）；完成守卫解决"没做完就交卷"。
   把这三点组合成 **v9** 后：qwen 用 **146 次请求 / 337K 输入 token** 完成 7/8（唯一失败是长输出提前交卷），
   deepseek **8/8**，保真度 **0.90**——是全部版本里最省、也记得最牢的。

## 1. 本轮新增的测试维度

### 1.1 百万级上下文编程任务（`million_repo`）

确定性生成的 Python 结算单仓：

| 指标 | 值 |
|---|---|
| 文件数 | 1,287（`atlas/core` 10、`atlas/services` 950、`atlas/vendor` 130、`docs` 190、tests） |
| 体积 | 3.57 MB |
| token 估算 | **992,136** |
| 缺陷 | `atlas/services/svc_0173.py::convert_units` 用 `*` 代替 `* 100`（major→minor 换算方向错） |
| 判据 | `python3 -m unittest discover -s tests` 两个测试全过 |

任务本身**不告诉**模型缺陷在哪个文件，只给测试失败的输出。模型必须 grep 定位、只读需要的切片。

|---|---|---|---|---|---|
| qwen3.7-flash | FHA | 1.00 | **10** | 2,965 | **20,782** |
| qwen3.7-flash | EoCC | 1.00 | 10 | 2,881 | 20,642 |
| qwen3.7-flash | SAC v5 | 1.00 | 80 | 2,090 | 144,712 |

| deepseek-v4.1-flash | FHA | 1.00 | **8** | 4,237 | **24,249** |
| deepseek-v4.1-flash | EoCC | 1.00 | 11 | 4,389 | 33,677 |
| deepseek-v4.1-flash | SAC v5 | 1.00 | 80 | 2,330 | 162,267 |
| deepseek-v4.1-flash | SAC v6 | 1.00 | **16** | 2,829 | 37,698 |
| deepseek-v4.1-flash | SAC v8 | 1.00 | 16 | 3,226 | 41,699 |

**读法**

- 992K token 的仓库，**所有范式都用 3–4K 的上下文解决了**：`grep` + 窄读把"长输入"变成了"短动作"。
  这就是论文 RQ2 的机制，在百万级规模上依然成立。
- **SAC 在这个任务上是纯开销**：v5 的 80 次请求是 FHA 的 8–10 倍，输入 token 多 6–7 倍。
  原因是每步都要额外一次状态更新，而历史本来就没什么可省的。
- v6 把差距从 8× 压到 1.6–2.7×（16–27 次请求），这是"合并调用"的直接收益。

**结论**：是否启用 SAC 应该看**历史是否增长**，而不是输入是否很大。

## 4. 四轮迭代（v5 → v8）

每轮只加一个机制，8 个任务（7 个旧任务 + `million_repo`）× 2 个模型 = 16 个单元；v9 是第 5 个版本，用来验证"推荐组合"。

| 版本 | 机制 | 模型 | 通过 | 平均分 | 触顶 | 峰值均值 | 总输入 tok | 请求数 |
|---|---|---|---|---|---|---|---|---|
| v5 | 子目标清单（模型规划 + `check` 工具） | qwen | 5/8 | 0.66 | 3 | 2,057 | 1,030,118 | 485 |
| v5 | 同上 | deepseek | 7/8 | 0.88 | 1 | 2,488 | 1,032,313 | 415 |
| **v6** | **+ 内联状态（状态更新并进动作调用）** | qwen | **8/8** | **1.00** | **0** | 3,708 | **389,319** | **156** |
| **v6** | 同上 | deepseek | **8/8** | **1.00** | **0** | 3,641 | 540,440 | 162 |
| v7 | + 读缓存（重复读返回缓存提示） | qwen | 8/8 | 1.00 | 0 | 3,608 | 464,390 | 180 |
| v7 | 同上 | deepseek | 7/8 | 0.97 | 0 | 3,745 | 449,521 | 148 |
| v8 | + 完成守卫 + 全量命令账本 | qwen | 7/8 | 0.88 | 1 | 4,484 | 702,734 | 252 |
| v8 | 同上 | deepseek | **8/8** | **1.00** | 0 | 4,375 | 562,524 | 159 |
| v9 | v6 流水线 + 全量命令账本（无守卫/无缓存） | qwen | 7/8 | 0.90 | 0 | 4,324 | **336,951** | **146** |
| v9 | 同上 | deepseek | **8/8** | **1.00** | 0 | 3,642 | 457,559 | 160 |

### 4.1 v5：子目标清单

- 加了一次规划调用，把 3–8 个子目标固定渲染在每个请求里，并提供 `check(index)` 工具。
- 效果：deepseek 7/8（比第一轮 v4 的 7/7 口径不同，任务集多了 `million_repo`），qwen 5/8。
- 问题：清单是"软"的——模型可以无视它直接 `finish`；且每步仍要一次独立状态调用，**请求数 485**。

### 4.2 v6：内联状态（本轮的关键突破）

**机制**：不再"动作一次 + 状态一次"，而是把状态写进**下一次**动作回复的开头：

```
请求 N+1 = [system, 任务 + 状态 + 清单] + 上一步的完整轨迹
模型回复 = <state>更新后的状态</state> + 工具调用
```

状态由**下一步**的回复顺手写出来，覆盖上一步的观测——这就是 1 次调用/步的流水线。

- 请求数 **485→156**（qwen，−68%）、**415→162**（deepseek，−61%）；
- 输入 token **1.03M→0.39M**（qwen，−62%）；
- qwen 从 5/8 变成 **8/8**，两个模型首次全绿。
- 代价：峰值上下文 2.0K→3.7K（因为要带上前一步的轨迹），仍远低于 130K。

**为什么有效**：qwen 之前失败的原因是"状态更新调用本身也会跑飞"（空状态、幻觉工具调用）。
把状态写进动作回复后，模型在**有明确下一步目标**的语境里写摘要，质量更高，也省掉一次往返。

### 4.3 v7：读缓存

- `read_file` 命中同一 `path+offset+limit` 时返回 `[cache]` 提示而不是内容。
- 结果：qwen 仍 8/8，但请求 156→180、输入 token 389K→464K（**反而变差**）；
  deepseek 8/8→7/8。缓存提示让模型转向别的读法（换 offset 重读），没有真正减少工作量。
- 结论：**读缓存要配合"文件级"粒度才有用**，按 `offset` 粒度的命中率太低。

### 4.4 v8：完成守卫 + 全量命令账本

- **完成守卫**：`finish` 时若清单仍有未勾选项，最多拦两次并要求继续。直接针对 qwen"没算完就交卷"。
- **全量命令账本**：LEDGER 里保留最多 40 条历史命令（v4–v7 只留 4 条），让命令不再依赖模型记忆。
- 结果：deepseek 8/8 且请求 159（与 v6 持平）；qwen 7/8，请求 252（比 v6 多 62%）——
  守卫让 qwen 多跑了很多步，且在 `swe_multifile` 上把 `orders.total` 改坏了（测试直接 import 失败）。
- 结论：**守卫对"想早交卷"的模型有效，但会放大步数**；全量账本是保真度的关键（0.19→0.73，真实会话保真度测试）。

### 4.5 排名与组合建议

| 维度 | 最佳 | 数字 |
|---|---|---|
| 准确率（无短板） | **v6** | 两模型 8/8 |
| 效率（请求 / 输入 token） | **v9** | qwen 146 请求 / 337K token（v5 是 485 / 1.03M） |
| 状态保真度（真实会话测试） | **v9** | 0.90（v1 为 0.19） |
| 最差 | v5 | qwen 5/8，485 请求 |

**v9 是"推荐组合"的验证**：它 = v6 的流水线 + 全量命令账本，去掉读缓存和完成守卫。
结果证明两个判断都对——账本把保真度从 0.47 推到 **0.90**，去掉守卫让请求数从 252 降到 **146**；
代价是 qwen 在 `long_output` 上**提前交卷**（0.2 分），这正是守卫要解决的问题。

**因此最终建议**：默认用 v9，把完成守卫做成**按任务类型开启**（有明确清单/结构要求的长输出任务开启，
其余关闭），这样既保留效率又不丢"没做完就交卷"的防护。

## 5. 结论与优化方向

### 5.1 本轮验证有效的（按收益排序）

1. **内联状态（v6）**：请求 −60~68%、输入 token −62%（qwen）、准确率 8/8。这是本轮唯一"又多快又好"的改动。
2. **机器账本**（v4 引入、v8 扩展为全量命令）：让"做过什么"不再依赖模型记忆，是保真度的唯一可靠来源。
3. **子目标清单（v5）**：对 deepseek 有帮助（7/8），对 qwen 需要配合守卫；单独用收益有限。
4. **完成守卫（v8）**：能阻止"没算完就交卷"，但代价是步数上升，适合放在"宁可多跑几步"的场景。

### 5.2 被证伪或需要修正的

- **读缓存（v7）**：按 `offset` 粒度的缓存命中率太低，反而诱导模型换姿势重读。应改为**文件级 + mtime**。
- **SAC 在长输入任务上不划算**：百万级仓库里 FHA 用 8–10 次请求就解决了，SAC 需要 16–80 次。
  正确的策略是**按需启用**：历史会增长（长程/多轮）时用 SAC；一次性长输入用选择性阅读即可。

### 5.3 下一步（按预期收益）

1. **状态更新与动作合并的进一步压缩**：v6 已经 1 次调用/步，但一次调用仍要重发"任务 + 状态 + 清单"。
   可以把清单/锚点做成**不可变前缀**（缓存友好），预计再降 20–30% 输入 token。
2. **文件级读缓存**：记录 `path → mtime`，命中直接返回"已读过，见状态"，并让状态里的 FACTS 按文件聚合。
3. **按信息增量触发折叠**：v6 每步都写状态；对 `ls`/缓存命中等零信息步骤可以跳过，预计请求再降 15%。
4. **子目标清单自动化**：目前清单由模型规划；可以从任务文本 + 测试输出**自动派生**（例如测试名就是子目标），
   避免"清单漏项"。
5. **保真度基准的扩展**：本轮的 recall 只有 3 个会话 × 16 步，样本太小；应扩到 20+ 会话并报告置信区间。
6. **在 DSH 里实测**：插件仍是策略层 + 单元测试；下一步把它挂进 profile，用真实会话验证 v6 的流水线语义
   （DSH 的 `agent/pre-step` 是否允许把状态写进动作回复）。
